# Hackathon team workflow

## Suggested issue labels

`bug`, `enhancement`, `documentation`, `design`, `security`,
`good first issue`, `priority:P0`, `priority:P1`, `stretch`.

GitHub issue templates reference only the standard labels `bug` and
`enhancement`; create these in repository settings if missing.

## Board columns

Backlog → Ready → In progress → In review → Done.

## Working agreement

- One person owns an issue at a time; collaborate in PRs.
- Keep PRs small enough for a teammate to review quickly.
- Main should remain usable during the hackathon.
- Update the changelog under Unreleased as part of the change.
- For risky changes, describe an easy rollback path.
- Do not share secrets in team chat, issue screenshots or commits.

## Prioritisation

Focus on the seven core implementations and a complete demo flow first.
Treat the seven additional ideas as stretch goals, not launch blockers.

## Zentral Hack project records

The [Zentral Hack project documentation](hackathon/README.md) describes the two-person team's work from initial Miro ideation and feature planning through architecture and implementation. Actual planning artefacts, source commits and design decisions provide the basis for detailed attribution. The project documentation is written as a factual technical record, not as a pitch or submission guide.
